# 四视角拼接（DashcamStitch）

把行车记录仪同一时刻的 4 路视频（主视角 + 左/后/右）拼成一张画面，在手机上直接出片。

- 主视角在上，左/后/右在下，**几何上不裁剪、不拉伸**
- 相册里按文件名时间戳自动聚合"同一次录制"的多视角素材
- 可指定目标文件大小（默认 70MB），末尾 15 秒自动提高码率保证车牌可辨
- 输出直接进相册 `Movies/DashcamStitch/`

## 安装

```bash
adb install -r build/dashcam-stitch.apk
```

最低 Android 10（API 29），需要 arm64 设备 + 硬件 HEVC 编解码。

## 使用

1. 打开 App，授予"读取/写入存储"权限
2. 列表里会按时间列出可拼接的素材组（显示 4 个视角缩略图和时长）
3. 点一组 → 选目标大小（默认 70MB）→ 可选填时长秒数 → 开始
4. 进度条走完即可在相册里看到成片，也可以直接播放/分享

## 输出规格

| 项 | 值 |
|---|---|
| 分辨率 | 取 min(理想画布, 设备编码器上限)。P30 上是 3076×2160（理想画布 3840×2696） |
| 帧率 | 恒定 30fps（丢帧会用重复帧补齐，时长与源一致） |
| 编码 | HEVC（`hvc1`），不支持时退回 H.264 |
| 音轨 | 无（本项目素材为静音；如需保留音轨可在 `Composer` 里加一路 MediaMuxer track） |
| 体积 | 按目标大小自动算码率，实际约比目标小 8~10%；目标特别小时会自动降分辨率来达成 |

### 目标体积很小时会怎样

硬件编码器有码率下限，硬压到很低会出现"目标 8MB 实际出 20MB"。所以当单位像素码率过低时，App 会自动：

1. 取消末尾 15 秒的提码率（否则均摊码率下不来）；
2. 按比例降低输出分辨率（最低到 1280 宽），让码率与像素匹配。

实测 8MB 目标 → 1722×1208 / 7.7MB；70MB 目标 → 3076×2160 / 63MB。

### 为什么不是 3840×2696

理想画布是 3840×2696（主视角 3840×1696 + 三路侧视角 1280×1000 等分）。但手机硬件 HEVC 编码器的最大高度通常是 2160，`MediaCodec` 会拒绝更大的尺寸，所以 App 会自动等比缩到编码器支持的最大尺寸。画质损失很小（见 `docs/` 里的对比图）。

## 技术实现

```
MediaCodec 硬解 × 4  →  SurfaceTexture(OES)  →  GL 画布（xstack 等价布局）
                                                  →  编码器 input Surface（零拷贝）
                                                  →  MediaMuxer → MediaStore
```

几个关键点（踩过的坑）：

1. **解码器会跑得比渲染快**：SurfaceTexture 只保留最新帧，不节流就会丢掉一半的帧。
   这里用"在途帧数 ≤ 2"的方式喂输入：消费一帧才喂一帧，保证 1:1。
2. **CFR 补齐**：万一某帧还是丢了，按 PTS 跳变补重复帧，保证输出严格 30fps 且总时长不变。
3. **编码器尺寸上限**：`VideoCapabilities.isSizeSupported()` 不通过时按比例缩到支持的最大尺寸。
4. **硬件解码实例不够**：创建失败会自动回退到软件解码器。
5. **Huawei 设备的 `setParameters(KEY_VIDEO_BITRATE)`** 可用，用来在末尾 15 秒提码率。
6. **失败必须算失败**：编码器 `onError`、封装器启动失败、30 秒等不到 EOS、一帧都没写出去，都会抛异常 → UI 报失败并删掉半成品，不会把 0 字节文件标成"拼接完成"。
7. **进程被杀留下的孤儿文件**：启动时清理 `Movies/DashcamStitch/` 下"MediaStore 里没有正式记录"的 `STITCH_*.mp4`（超过 60 秒的），避免碎片长期占用空间。
8. **解码看门狗**：15 秒没有首帧、30 秒没有新帧直接中止，避免界面无限转圈。

## 构建

不依赖 Gradle，直接调 SDK 工具链：

```bash
./build.sh          # aapt2 → javac → d8 → zipalign → apksigner
```

需要 `ANDROID_SDK_ROOT`（默认 `~/Android/Sdk`）和 JDK 17（默认 `~/.jdks/temurin-17.0.12`）。

## 目录

```
AndroidManifest.xml
res/                     布局、字符串、图标
java/com/dashcam/stitch/
  MainActivity.java      相册扫描结果列表 + 参数对话框
  MediaScanner.java      按文件名时间戳聚合多视角
  StitchActivity.java    进度页 / 保存到相册 / 播放分享
  Composer.java          解码-合成-编码主流程
  GroupAdapter.java      列表适配器
  ThumbCache.java        缩略图缓存
  gl/EglCore.java        EGL14 封装
  gl/CanvasRenderer.java 四路纹理按模板绘制到画布
build.sh                 构建脚本
```

## 测试

`test/` 下有真机自动化脚本和测试报告：

```bash
./test/run_tests.sh          # 需要设备已连接、APP 已安装
```

覆盖：基准 105s、限长、超长请求、极小/极大目标体积、取消、进程被杀、连续多次、息屏、对话框可读性、结果页信息。

## 已知限制

- 只实现了"主上/三下"一种排版；2×2 等模板在 `CanvasRenderer.draw()` 里加坐标即可
- 4 路 4K 并发解码对低端机型压力大，可能需要降级（当前会自动退到软件解码）
- 编码时长为实时左右：1:45 素材约 75~90 秒出片
- 没有前台 Service：切到后台/锁屏**通常**能继续（实测息屏可完成），但极端内存压力下仍可能被系统回收，此时会在下次启动被当作孤儿文件清理掉
- 目标体积有物理下限：105 秒、4K 画布下约 9~10MB，再小只能靠降分辨率（已自动处理）
- 孤儿文件清理只在 **App 冷启动** 时执行；如果进程被杀后只是把仍在后台的 App 拉到前台，要等下一次冷启动才会清（不影响使用）
